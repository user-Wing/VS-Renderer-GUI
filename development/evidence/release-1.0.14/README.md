# 1.0.14 本地更新验证

本轮按 `10.23.md` 的 VSP 部分实施；网站事项跳过。没有制作发行压缩包、上传代码或修改远端 Release；既有用户配置、VPY、ICC/LUT 与媒体保留。

## 4070 Laptop：1080p23.976 → 2160p47.952

素材为用户指定的 Heya Camp 第 1 集，实测输入 1920×1080、24000/1001。播放器测试在 3840×2160 物理输出面上，跳转到 30 秒、预热 7 秒、测量 30 秒。计数取 Native 接收与 VS 跳帧，不能用重复 Present 次数代替视频帧数。

| 链路 | Native 接收 fps | VS 跳帧 | 结论 |
| --- | ---: | ---: | --- |
| A4K2160 → 整帧960×540 RIFE → A4K2160 | 22.161 | 776 | 未达标 |
| A4K2160 → 整帧960×540 RIFE → Jinc2160 | 47.933 | 0 | 达标；Native 丢弃/合并均 0 |
| A4K2160 → 整帧960×540 RIFE → D3D11 2160 | 47.967 | 0 | 达标；Native 丢弃/合并均 0 |
| 1080 → 半尺寸 RIFE 推理、保留原帧 → A4K2160 | 42.700 | 160 | 未达标 |

前三项将所有帧缩到 540p，原帧细节也降低；不能将其达标说成保留了 2160 超分细节。只降低 RIFE 推理尺寸、保留 2160 原帧的旧链，VS 离线出帧约 29.8～30.9 fps，也未达目标。保留 1080 原帧的末端 A4K 链，平面420优化后离线曾达到 56.49 fps，实际播放器只有 42.70 fps，故不推荐将离线数字当作实时承诺。8 线程对照反而下降，未作为默认设置。

优化将原 Shader 的 RGB48 打包、同步回读、CPU 拆平面，改为 GPU 生成 YUV 平面并合并等待；B 链可输出 420，降低传输字节。Qt 嵌入式加载需使用 Windows 原生路径预载隔离依赖，否则会静默落回旧插件。两种后端的真实帧像素对照通过当前容差，所测最大差为 32/65535；不宣称逐位一致或 420/444 等价。

## NuxBox：7840HS / 780M

原始 dav1d 源码位于 `C:\Private\ffmpeg-native\deps-full\dav1d`，保持不变；另建固定提交工作树与 MSVC 构建。8K48 AV1 10-bit 样本共 1087 帧，统一 16 线程、filmgrain=1。

- 原版 CLI 三轮约 41.63 / 40.46 / 40.90 fps，新版约 43.37 / 41.74 / 43.01 fps，配对平均提升约 4.2%，仍不达 48 fps。
- 完整解码像素 MD5 均为 `65a380176a860c55007ba3ee377ff094`。
- 已用相同 FFmpeg 对象代码分别链接新旧 dav1d，生成独立最小解码测试 EXE；FFmpeg 端到端吞吐波动较大，新版没有稳定提升，故不替换原有 FFmpeg。
- 新版 FFmpeg SHA-256 为 `6c98130168886ffcf7798a39205ba0b3d8c03726146df5be4e5be530da77e823`。它是 AV1 解码测试构建，不能替代含完整编码器/滤镜的个人 FFmpeg。

780M 使用独立复制的 Python/VS 运行时实测 no CNN + 两项额外增强，各 480 帧；原分离链对比合并 hooks + 平面回读：

| 输出 | 原链 fps | 优化链 fps | 范围 |
| --- | ---: | ---: | --- |
| 1920×1080 | 40.826 | 59.561 | VS 出帧吞吐达到 48 fps |
| 3840×2160 | 17.446 | 38.509 | VS 出帧吞吐未达到 48 fps |

这些数字不含 Native 上传/呈现。此前 FFmpeg Vulkan 的同类对照也留存，但不能与 VS 数字混用。远端原始日志、独立 EXE 和运行时保留于 `D:\VSP-1.0.14-validation`（本机入口 `Z:\ARXChem\D\VSP-1.0.14-validation`）；源媒体和原软件未改。
